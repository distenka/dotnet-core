Executive Summary

What the current repository is, how far it is from the current Distenka platform, and the recommended path.

What the current “client SDK” actually is

The repository (github.com/distenka/dotnet-core, HEAD 3eda536 release v1.0.0) is a fork of the Runly job framework: a processor host that job authors compile against. It provides Processor<TConfig[,TItem[,T1..T16]]> base classes, an execution pipeline (initialize → enumerate items → process in parallel with retries → finalize), a JSON Config model, DI integration and a CLI with three verbs — list, get, run. The compiled Distenka.dll is the assembly the platform's executor launches inside the Kubernetes sandbox (dotnet <dll> run <config>) and interrogates at upload time (dotnet exec <dll> list).

The only code that ever talked to a platform — a SignalR channel to https://{org}.{env}.distenka.ai with an API key — was removed in commit 856048c (“stry-37 remove client api connection to be added to client package”). That client package was never created. The repo therefore contains no platform client, and test/Client.Tests still points at a project that does not exist.

How it differs from what Distenka needs today

  • Executor contract mismatch (P0). list prints a banner plus default-config instances, not the ACC-36 descriptor schema the platform compiles (PluginInputSchema); every package built with this SDK publishes an unusable schema and cannot be invoked. run always exits 0 — even on Disposition.Failed — so the executor marks failed runs Completed. run crashes with a NullReferenceException when the configuration lacks a process key, which the platform's configuration document never has.
  • Invisible logging. ProcessorHost removes the console logger; processor ILogger output never reaches the run log. Spectre spinners write to a non-TTY pipe.
  • Obsolete model. ExecutionConfig.OrgName/APIKey/Env/RunId and DistenkaApiConfig (default https://api.distenka.ai/) encode the abandoned multi-tenant hosted design and violate the on-premises/no-HQ rule.
  • Missing client. No submission, status, cancellation, invocation, result-capability or webhook support for the real API (POST /api/runs, GET /api/runs/{id}/details, /v1/invoke, /api/runs/result, Bearer DK-/DKI-/drc1).
  • Model mismatch now decided. The platform treats one uploaded package as one processorId but already reads a process name from the run configuration; the SDK supports many processors per assembly. AD-7 settles it (one processor per package, N processes identified by process); the per-process schema gap under ACC-36 is OQ-9.

Recommendation

Split and modernize, don't rewrite. Keep the processor host (it is sound, well-documented code and the platform depends on its CLI shape) and keep its package identity Distenka (AD-12), but make it executor-compatible: descriptor schema (one package = one processor exposing N processes, AD-7), exit codes mirroring the executor exactly (AD-3), stdout logging, configuration without the obsolete fields. Create a new, dependency-light Distenka.Client (System.Text.Json, IHttpClientFactory, net8.0 + netstandard2.0) over the public REST contracts only, authenticated with a DK- key supplied as a runtime secret (AD-9). Ship Distenka.Processor.Testing with an executor-contract harness so authors can validate packages before upload. Release as 2.0.0 with a migration guide.

Decisions applied 2026-10-31 (section 06): no SignalR — results are read over REST by run id (AD-8); no account login, JWT or key management (AD-9); scheduling out of scope (AD-10); Distenka provenance recorded, formal licence pending approval (AD-11); PackageId stays Distenka (AD-12). AD-13: no dedicated logs API — `details.output`/`timeline` are the log surface (OQ-3b resolved). Still open with the platform team: device events (OQ-5b), licence text (OQ-6b), termination/SIGTERM semantics (OQ-8), per-process schema (OQ-9).

Phase 0 decisions, blockers and investigations

    All Phase 0 P0 decision stories are Done (DCS-001 to DCS-004, DCS-006, DCS-009); the P1 decision stories DCS-005, DCS-007 and DCS-008 are Ready. One story is Blocked on a platform-side answer (DCS-047 — OQ-8 termination semantics) and one needs investigation of an undocumented route (DCS-032). DCS-026, DCS-071 and DCS-072 are archived (Out of Scope / Superseded) and are not counted as active work.

          Validation & Release Plan

          How the work is proven and shipped.

          Testing strategy

          • Unit — descriptor mapping per CLR type; ConfigReader resolution; retry/threshold/parallel/cancel semantics (DiagnosticProcessor); client DTO round-trips from the JSON examples in docs/api-*.md; error-code mapping; retry policy behaviour per code; webhook HMAC vectors; credential shape/redaction.
          • Executor-contract — spawn built packages exactly as the executor does (cleared env, list / run), apply its rules verbatim (first JSON object, ParseLogLevel, exitCode == 0 && !hasPluginErrors, stderr) and assert the Completed/Failed verdict for every SDK outcome — the agreement tests required by Decision 2 (DCS-093/DCS-100). Pinned to the executor commit it mirrors. Platform SIGTERM behaviour is excluded until OQ-8 is answered (DCS-047).
          • Contract (client) — scripted HTTP handler seeded with every documented status/header/body (202, 200 replay, 304, 400, 401, 402, 403, 404, 409×2, 413, 429×3, 503).
          • Integration — opt-in suite against a dev platform: submit→wait→cancel; invoke→result→callback; package upload + validation + published_schema equality.
          • Template & samples — generated project builds; Echo sample validates and runs.

          Compatibility requirements

          • Processor host: net8.0, runnable by dotnet <dll> on the executor image; no reliance on environment variables; ≤ 256 MB heap; output ≤ 2000 lines.
          • Client: net8.0 and netstandard2.0; no Newtonsoft, Spectre, System.CommandLine, ASP.NET or SignalR dependencies (AD-8); TLS only by default; DK- key never compiled in (AD-9).
          • Platform contracts pinned to the ACC/DST/CAP story ids cited in each DCS story; re-verify on platform upgrades.
          • Breaking changes documented in docs/migration-2.0.md; old NuGet versions deprecated with a pointer.

          NuGet packaging

          • Packages: Distenka (processor host — PackageId retained, AD-12), Distenka.Client, Distenka.Processor.Testing, Distenka.Templates, Distenka.Diagnostics (tool).
          • MinVer from v* tags; deterministic builds; SourceLink; snupkg symbols; XML docs; README in package; Distenka provenance metadata (AD-11); licence expression only once approved (OQ-6b); no pre-release dependencies.
          • Layout check: a processor built with the package packs to tools/net8.0/any/ with Distenka.dll alongside the job assembly.

          Documentation

          • README (two quickstarts, executor contract, scope), docs/adr/*, docs/errors.md, docs/migration-2.0.md, XML docs for every public member.
          • All snippets compiled in CI; no dead links; no platform marketing claims.
